## Comment by @tomusdrw

Why not ditch defaults and always pass things explicitly? Having defaults in this specification implies that the defaults might be relied upon at some point, and it seems like one extra moving part without any means to properly verify if an implementation is actually adhering to these defaults.

I'd also suggest that the expected behavior of fuzz targets when these variables are not present is to refuse to start - this allows catching errors (typos or misconfiguration) in passing these variables over multiple layers easily.

If there is an argument to keep the defaults, I'd suggest changing the language here to explicitly require the implementations to follow these (`MUST`), since they will be relied upon.

## Comment by @davxy

This is just legacy infrastructure for targets using CLI args. The {TARGET_SOCK} in placeholder in `targets.json` exists only to continue to support older targets during migration. New targets adopting the standard packaging will receive configuration exclusively via environment variables, so this placeholder substitution won't apply to them. Eventually this code will be removed as targets migrate to the standard way.
So you can ignore it (the web app doesn't even use target.py)
