# [Fuzz Proto] PVM tracing feature

## Pull Request by @sourabhniyogi

If PVM Tracing is supported by the target (via `feature-pvm-tracing`), the fuzzer may attempt to resolve disputes in accumulation state root matches, work report matching, and authorization output with a `GetPVMTrace` message for which the target must respond with a `PVMTrace`.

This fuzzer protocol feature hopes to replace the manual process of "hey, does anyone have a trace for XXXX" (wherein the traces have no standard format and requires tedious script writing and reasoning) with a standard format amenable to dispute reporting.  This feature may be used for fuzzing of accumulate, refine and authorize invocations and has filtering to support the rapid detection of differences in very large gas usage (3.5-5B) in the majority of naturally occurring cases but is not intended to be absolutely perfect.


## Comment by @sierkov

@sourabhniyogi Thanks for raising this and suggesting a solution! I see this as important not only for speeding up development cycles but also for reducing the risk of unintentionally disclosing implementation details through manually crafted PVM logs.

Here are a few adjustments I’d propose for consideration:
- **Provide a CLI-level API (instead of extending the Fuzzer API)**
  For example, commands that take a trace file (which all implementations already support) and produce a PVM trace:
  ```
  pvm-block-trace <input-trace.bin> <output-pvm.json|bin>
  pvm-refine-trace <input-trace.bin> <output-pvm.json|bin>
  ```
  This keeps the Fuzzer API clean and focused, and makes it easy to deploy and iterate with the PVM trace support and syntax.
  ```scripts/target.sh``` in this repo already makes downloading and running any implementation locally straightforward.
- **Adjust the file trace format**
  - Record register updates instead of dumping all values (compact, human-readable).
  - Record memory updates (makes debugging misbehaving host calls easier).
  See sample ASN.1 syntax below.
- **Skip filtering for now**
  The compact representation should keep even the largest Refine traces manageable (~20 GB) — it should be possible to parse them in a few seconds on a modern CPU. Also, they should compress well for network transmission.

```asn1
U32 ::= INTEGER (0..4294967295)
U64 ::= INTEGER (0..18446744073709551615)
I64 ::= INTEGER (-9223372036854775808..9223372036854775807)

ByteSequence ::= OCTET STRING
AddressValue ::= U32
RegisterIndex ::= INTEGER (0..12)
RegisterValue ::= U64
GasRemainingValue ::= I64

MemoryChunk ::= SEQUENCE {
  address AddressValue,
  bytes   ByteSequence
}

RegisterUpdate ::= SEQUENCE {
  register RegisterIndex,
  value    RegisterValue
}

InstructionTrace ::= SEQUENCE {
  code             ByteSequence, -- opcode + parameters
  updatedRegisters SEQUENCE (SIZE(0..13)) OF RegisterUpdate, -- unique and sorted
  updatedMemory    MemoryChunk OPTIONAL,
  newPC            RegisterValue,
  newGas           GasRemainingValue
}

ExecutionTrace ::= SEQUENCE OF InstructionTrace
```

## Comment by @sierkov

@jaymansfield The MemoryChunk simply records the address and the bytes written by a store instruction (up to 8 bytes).
This information should be readily available in any implementation. In fact, the space savings from storing only the changed registers should more than offset the cost of including these memory writes — and only a fraction of all instructions are stores anyway.

My goal is to make the format **complete** for all PVM and host call debugging use cases, minimizing the risk of future adjustments that every implementation would need to adopt.

If you have specific counterexamples, I’d be happy to analyze them.

P.S. Given the simplicity of the PVM instruction set, it’s possible that any memory store is always preceded by register updates that make it clear what data is being written and where. That said, I haven’t analyzed this deeply enough to be certain. Perhaps @koute could weigh in here?

@koute — we’re working toward a shared PVM trace format across implementations to make it easier to share and compare divergent traces. Do you have any suggestions or concerns?


## Comment by @sourabhniyogi

@sierkov (+@jaymansfield) Thank you for your comments =) --  Having `MemoryChunk` logging for the address/bytes written per store is a simple great idea -- I'll add it in the next day.  I think its useful for both STORE _and_ LOADs, and not just STOREs.

For `updatedRegisters of RegisterUpdate` I understand the RegisterUpdate is a huge redundancy reduction in addition to "what really changed" reasoning when manually looking at logs.   But I wanted a fixed length record format (128-byte) for extremely rapid error-free implementation and to bring "oh, you/we encoded/decoded it wrong" engineering time to absolute zero, to the point where the fuzzer could jump to any step/gas with the simplest of procedure: "jump to 128 * the step#" from a PVM trace response, eliminating 100% of decoding ... I mean, we do enough of that already!    

In addition, I am imagining this jumping in a 128MB of response in memory being not a problem with sampling every few 100-5K steps.  20GB of log being in memory, in our experience, is not that quickly written or decoded, I want to minimize engineering time on encoding/decoding by all teams.  With any sampling process that has this 128MB representing a subset of the full step-by-step log (5B x 128 bytes = 640GB), if you only get the register updates that specific sample (typically 0 or 1 except for ecalli) rather than all 13 registers, you are far less likely to get a clear picture between samples:  This is because I have a "sampling" process keeping a 128MB low resolution view of the total steps in mind as the discovery process, followed a high resolution "where do we really disagree" (where your `MemoryChunk` will be used).    Does that make sense?  

I suspect it will help to look ahead to _basic blocks_ in the 3.5B - 5B gas usage in accumulate + refine, with the full expectation that basic blocks will be fundamental unit of gas accounting very soon (@koute can speak to when): the basic block level gas measurement itself gives an early warning -- because any little difference in gas of basic block will reveal things even more quickly than register checking.   We have done 3.5B gas refines this summer (to see if our recompiler traces matched that of our interpreter), and found that by adding an ecalli every 10K basic blocks (with a # of basic blocks counter in addition to gas in our "VM Context"), we could also reasonably record full registers sanely from the recompiler as well, where logging register updates is not practical (at least, for us).    What we've seen is that the average basic block is typically like 10 instructions in normal programs, so 3.5B-5B gas is like 350MM-500MM basic blocks.  If the fuzzer samples the target every 10K basic blocks (~100K gas), a 3.5B-5B execution is 50K samples (5B/100K) -- which if you keep at 128 bytes/sample is just 6.4MB.  Once the fuzzer identifies which sample is the first difference from this (up to 6.4MB), the fuzzer simply asks for the step-by-step dump for the 100K gas preceding -- 12.8MB -- which can include the `MemoryChunk`.  

We aren't doing billions of gas yet, but we've seen a few cases of millions already and we should aim for the big cases when designing this well -- yes?


## Comment by @koute

I'm not entirely convinced this should be a part of the fuzzer protocol, but I'll leave that decision up to @davxy.

Nevertheless, here's a few suggestions:

1. Having a non-binary format is probably worthless due to how slow and bloated it would be, so I wouldn't bother. Make it binary-only.
2. I would suggest calling this "PVM binary execution logs" or something like that. There will be an "official" tracing format in the future, but that will be for debugging PVM *programs*, so it will *not* log redundant informations like e.g. which instructions were executed, register reads/writes or memory accesses, gas consumed, etc. (the idea is that for any program running on a PVM you'll be able to dump its execution trace without impacting the execution speed at all, and then reexecute and debug the program later, so only non-deterministic parts of the execution like e.g. memory read/writes from *inside* of host functions will be stored; this will assume the PVM itself is compliant with the spec).
3. I would use a structure of arrays for storing this data instead of an array of structures, and store each kind of data in a separate file. For example, for every instruction executed you would append a single `u32` with the instruction address to an array, so you'd have a single file composed of just `[u32; N]` where `N` is the number of instructions executed. For gas charging you'd store `[(u32, i64); N]` where you'd store the instruction pointer and the new amount of gas, and `N` would be the number of times the gas counter was changed, etc. This has a few benefits: very fast to write and process (because the structures are all constant length), simple (no complicated data structures), easier to compress, and you can selectively log/compare/implement only certain things (e.g. let's say in your implementation dumping memory writes is awkward - okay, you don't have to implement this, but you can still compare the other execution logs you've implemented; or maybe the program you're running is huge, so don't want/need to dump all of the data because it'd take forever, etc.)
