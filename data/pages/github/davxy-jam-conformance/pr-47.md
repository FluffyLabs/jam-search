## Comment by @davxy

> if we'll have tests about fork, if it is possible to make the generated trace a chain instead of a block, it's would be tricky to introduce tests that adapt block per file & multiple blocks from different files, and it would be best if there will be a single folder just for the fork tests

Each trace folder contains multiple files, where **each file represents a single fuzzer step**.  
The steps are numbered and should be processed sequentially.  

It does not matter if the steps form a fork (or multiple forks) or not.  
If handling forks is a problem, that is an implementation limitation that should be addressed --  
it is certainly possible, as teams are aligning on using the fork feature.  

Another case to consider: if your target triggers a fault after importing 10 blocks in sequence,  
but does NOT trigger the fault when only the last step is imported.  
This is a bug -- in such a case, the trace folder will contain all 10 steps, not just the last one.  
We have already seen an example of this in the past:  https://github.com/davxy/jam-conformance/tree/main/fuzz-reports/0.6.7/traces/1754983524.

## Comment by @davxy

I just modified the protocol so that the `Error` variant now includes a message.  
The overhead is negligible (essentially an extra `0` when no message is provided),  
but if used it could save time during debugging.

**NOTE:** When an `Error` message is returned, the fuzzer excludes the last block from import time benchmarking.  
This means you can include a message without worrying about it affecting your performance by a few microseconds :-D
