## Comment by @sierkov

@davxy I confirm that TurboJam passes all test vectors from ```fix-lookup-anchor-slot``` branch.

Regarding the disabling of ```(11.38)``` during test vector execution, are there any other strong reasons for keeping it disabled, apart from the fact that the ancestry set is not provided in the current test vectors?

From my point of view, reducing the number of disabled checks is generally a positive thing, as it prevents untested sections of the specification from making their way into production.

In this particular case, if explicitly adding ancestry to the test vectors is too complex, what about the following approach to establishing a minimally viable ancestry while keeping the current test vectors unchanged?

If no ancestry has been provided:
1. Register the genesis block at slot 0 in the ancestry.
2. Register all blocks from beta in the ancestry.
3. Set the state_root of the last block in the ancestry to the current state root (since the state_root of the last block in beta is ```H_0```).

The above is what TurboJam does currently and how I caught the issue.

In my view, this would allow ```(11.38)``` to become a regular rule that does not require manual enabling and disabling, thus reducing the risk of a misconfigured client accidentally making its way into production in some implementations.
