@ascrivener @jaymansfield I'm not sure why deserialization would ever be necessary in this context.

First of all, it's important to clarify that computing the state root from raw key-value items (prior or posterior) doesn't require deserialization. But you need the serialized stuff.

In practice, test vectors block processing involves:
1. Taking the provided raw KV items,
2. Writing them directly into storage as-is,
3. Executing the block,
4. Producing the resulting (posterior) state and its corresponding state root,
5. Verifying that the resulting KV state matches the expected output.

The raw KV state data is self-sufficientit and contains all the information needed to compute the posterior state given the block. There’s no hidden or additional state required.

If you *do* find yourself needing to deserialize, it might be to interpret the key’s prefix and determine whether it refers to a storage item, a preimage, or a lookup. These are not ambiguous and you can easily spot what is what.
For serialized lookup entries like $a_l$ (assuming a valid pre-state), there are two cases:
1. The associated $a_p$ is already present in the prior state. The protocol ensures that for each $a_p$, there's a corresponding $a_l$. If needed, you can reconstruct the corresponding $a_l$ keys from each $a_p$ value.
2. The $a_p$ (for some $a_l$) is not yet present, in this case it may be introduced by a preimage extrinsic in the block. Again, the same check applies - verify whether $a_l$ exists for that preimage in the extrinsic.

If you want to validate the value associated with a particular $a_l$, you can recompute its key (e.g., using the hash-of-hash method described in D.2) and retrieve the value from the state.

In our implementation, we don't deserialize KV items, we write them as-is. And we access the $a_l$ items when required using the recomputed key (given a preimage hash).

Since we are able to execute random vectors (i.e. not sequentially), I expect that this is possible in general 🙂

Maybe @sourabhniyogi can also share its way to process these vectors?

Edit: this is the way warp sync works. I.e. you'll receive a bunch of raw key values to start from.

```go
// subscribeServiceData https://hackmd.io/@polkadot/jip2#subscribeServiceData

	StateKey  [31]byte      `json:"key"`

// subscribeServiceValue https://hackmd.io/@polkadot/jip2#subscribeServiceValue
type SubServiceValueUpdate struct {
	StateKey  [31]byte   `json:"key"`
	ServiceID uint32     `json:"serviceID"`
	Key       string     `json:"userKey"`
	Hash      common.Hash `json:"hash"` // k in host write and read
	Value     string     `json:"value"`
}

// subscribeServicePreimage https://hackmd.io/@polkadot/jip2#subscribeServicePreimage
type SubServicePreimageUpdate struct {
	StateKey  [31]byte   `json:"key"`
	ServiceID uint32     `json:"serviceID"`
	Hash      common.Hash `json:"hash"`
	Preimage  string     `json:"preimage"`
}

// subscribeServiceRequest https://hackmd.io/@polkadot/jip2#subscribeServiceRequest
type SubServiceRequestUpdate struct {
	StateKey  [31]byte    `json:"key"`
	ServiceID uint32      `json:"serviceID"`
	Hash      common.Hash `json:"hash"`
	Timeslots []uint32    `json:"timeslots"`
}
```

* SubServiceDataUpdate
* SubServiceValueUpdate
* SubServicePreimageUpdate
* SubServiceRequestUpdate

I believe this kind of "structured logging" of state updates makes sense for everyone to standardize on alongside this 31-byte state key.   The "original" data used to compute the StateKey C(s,h) is present in each.  You could also have a "pre-state" and "post-state" (for 3/4 since preimage makes little sense), which is even more useful for debugging, although that's not what JIP-2 does.

@clearloop 

Vals stats:
- There are 6 validators
- Validators stats struct has 6 items.
- Each val stat is encoded as 4 bytes.
- You record two of these structs (vals_last + vals_curr)
Thus you need: 6*6*4*2 = 288 bytes

Cores stats:
- There are 2 cores
- Cores stats struct has 8 items.
- each item is encoded using **compact encoding** (assume each item takes one byte)
Thus you need: 2*8 = 16 bytes

For services stats if there are 0 services then there is the 0 byte only
In total: 288 + 16 + 1 = 305

For services stats if there is 1 service:
- Service stats struct has 12 items
- each items is encoded using **compact encoding**(assume each takes one byte)
- Each key of the dictionary is encoded as 4 bytes (the service id)
- (note: dictionary is encoded as
In total: 288 + 16 + (1+4+12) = 320
