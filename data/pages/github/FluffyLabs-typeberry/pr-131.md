# Fix the prototype chain of classes returned by json-parser

## Pull Request by @tomusdrw

While working on parsing the codec test vectors I've realised that despite the fact that we are using `class`es to describe our core model, the JSON parser will be just returning plain objects that simply match the shape of the class.

This makes it more difficult to compare the objects and hinders some possibilities (like checking `instanceof`).

This PR introduces a `json.object` descriptor, which allows passing a constructor/builder function that converts a plain object into a properly typed object when reading stuff from JSON.

As a nice consequence this will also allow us to fix the snake_case vs camelCase notation and we will be able to use proper `constructors` for core data model (for instance `Block` constructor should just take `Header` and might start with empty `Extrinsic` arrays). For codec we will still need the generic `Record<T>` constructor, but I think it's a reasonable trade-off since codec is much more tightly coupled with the model than the JSON stuff.

On top of that I've introduced numeric types `U16/U32` by altering `Opaque` type wrapper a bit. I didn't use `Opaque` directly, because now it's possible to wrap `U16` again into `Opaque`, since I'm using a different identifier.

For collections I've introduced two types:
1. `KnownSizeArray` which is just a `Opaque` type that has an extra "human parseable" description of what the expected length of the array is.
2. `FixedSizeArray` which is actually a separate runtime object validating the expected length and preventing new items to be inserted (via `Object.seal`).

## Comment by @mateuszsikora

would it be possible to pass the class as a param instead of `Object.assign` ? I mean something like:

```ts
static fromJson = json.object<Block>(
    {
      header: Header.fromJson,
      extrinsic: Extrinsic.fromJson,
    },
    Block
  );
```


## Comment by @tomusdrw

Yes, I was considering that, but there are couple of reasons why I decided to go with builder function:
1. I'd prefer to keep JSON serialisation optional and separate from our core model.
2. Going with this approach you mentioned though requires a constructor (or a static function) directly in the core model just to convert data from JSON.
3. We already do that for codec (use constructor), but actually I had to change it in my WiP now to a static function, since we can only have one constructor.
4. `Object.assign` is a temporary solution and only works when the fields match exactly what we have in the object. In my WiP branch I already do conversion from snake case to camelCase and sometimes even renaming fields and in the builder function I can just use whatever constructor I prepared in the data model.

Hope this makes sense.
