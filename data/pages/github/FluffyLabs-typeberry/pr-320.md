# Run bandersnatch wasm in parallel workers.

## Pull Request by @tomusdrw

Related #313 

This PR introduces a little helper `@typeberry/concurrent` responsible for setting up a worker pool for tasks that should run concurrently.
It's super simple for now, but in the future we might considering switching to https://github.com/piscinajs/piscina

The "backend" is now customizable whenever needed and it seems that it mostly makes sense to optimize the JAM test vectors since they are doing a lot of signature verification at once. In production we might need to fine-tune that for particular cases (i.e. intiial block import = parallel, but later=synchronous).

I've run a bunch of non-very-scientific benchmarks to check optimal settings for now, and they confirm my suspicions.
There is a non-neglegible cost of simply running another worker (hundreds of ms it seems = probably wasm compilation + typescript + thread costs), so in case of simple unit tests it's better to have synchronous execution.

The startup time of a thread could be optimized a bit by sharing the compiled wasm module (see example here: https://github.com/paralin/reuse-wasm-module-demo/tree/master).

| workers (jam, bander, safrole) | JAM test vectors (safrole tiny + full) [ms]  | All unit tests [ms] | Unit test safrole [ms] |

| synchronous (sync, sync, sync)  | 25364.287834  |  27932.3295 | 1203.721708 |

| **8-8** (async, async, async)       | **3899.903417** | 31000.635333 | 5417.682542 |

| 4-8 (async, sync, sync)       | 5807.2745 | **27738.234166** | **1200.702** |
| 6-8 (async, sync, sync)       | 4425.274834 | N/A | N/A |

| 12-12 (async, sync, sync)       | 4417.007792 | N/A | N/A |
| 6-6 (async, sync, sync)       | 4873.841084 | N/A | N/A |


So after analyzing this data I went for `8-8` workers for JAM test vectors and synchronous execution for `bandersnatch.test.ts` and `safrole.test.ts`

## Comment by @tomusdrw

Note that this optimisation is currently useful only for running tests, and from the performance table you can see that it's not even all tests, but only w3f/jamduna test.

Optimizing for CI is also a valid point, but it would require a bit more ground work and benchmarking. I've changed the condition to be simply number of cores, since it's a small penalty locally and **should** run faster on CI, so 🤞.

In an actual network, the workflow is completely different. In a test network (like on JAM toaster, but note that not all cores will be available to us, JAM toaster will simulate a bunch of "small computers" doing network, so it will most likely be 4-8 core nodes), we have two different scenarios:
1. The initial sync, when we import a history of blocks between `0...N=CurrentBestBlock`. 
2. Maintaining sync (i.e. one block per 6 seconds) with the network - i.e. importing blocks as they come.

During the initial sync, it's good if we verify signatures of all of the blocks, but it's actually not required. It's enough if we validate signatures of the first block of every epoch (i.e. the ones with `epochMarker`), because the transitions in-between can be inferred to be valid. Most likely the bottleneck here will rather be a STF not signature verification. In such scenario we will most likely need a bunch of importing workers (I think that will be sub-processes) and each of the worker will have it's own verification instance.

During sync maintainance we will only import one block per 6 seconds (actually a bit more because of forks), so it's also not super useful there.
