# [codec] Type Descriptors

## Pull Request by @tomusdrw

This PR exposes an idea for expressing more complex types for encoding and decoding.

The idea is to have "Descriptors" for possible encoding/decoding types that can be composed into a more complex ones (sequence, optional & class).

The nice consequence of that is that we can use POJO objects for our data model and just augment it with the `Codec` details, like in the example below:
```ts
class TestHeader {
  static Codec = CLASS(TestHeader, {
    blockNumber: VAR_U64,
    parentHeaderHash: BYTES(32),
    priorStateRoot: BYTES(32),
    extrinsicHash: BYTES(32),
  });

  public readonly blockNumber: bigint;
  public readonly parentHeaderHash: Bytes<32>;
  public readonly priorStateRoot: Bytes<32>;
  public readonly extrinsicHash: Bytes<32>;

  constructor(o: Record<TestHeader>) {
    this.blockNumber = o.blockNumber;
    this.parentHeaderHash = o.parentHeaderHash;
    this.priorStateRoot = o.priorStateRoot;
    this.extrinsicHash = o.extrinsicHash;
  }
}
```

The mapping between the two is fully typesafe, when you change the field name or the type the descriptors need to be updated.

Given an object like above it's now possible to decode it or encode it:
```ts
// these two lines can potentially be moved to some static helper on `Codec`. 
const enc = Encoder.create({ expectedLength: TestHeader.Codec.sizeHintBytes});
TestHeader.Codec.encode(enc, new TestHeader( {...}));

// decoding
const testHeader: TestHeader = TestHeader.Codec.decode(Decoder.fromBytesBlob(enc.viewResult());
```

On top of that, this PR introduces a `View<TestHeader>` type which represents a lazy-decodable `TestHeader`.
Since it's not easy to figure out where exactly each field of `TestHeader` lies in the encoded bytes, I've decided for now to decode all of the prior fields to return the one that is requested.
This could be further optimised by introducing a `Skipper` instead of `Decoder`, where we actually read all the required data, but never create any data. This would introduce a bit more code though, and it's not clear if we really need this so we can leave that as an optimisation for future.

The `View` objects can be used like so:
```ts
const view: View<TestHeader> = TestHeader.Codec.View.fromBytesBlob(enc.viewResult());
const blockNumber = view.blockNumber(); // lazy decode the first field.
// Using methods is intentional over getters to emphasise that this operation is not cheap.
```

At any point in time, when the caller decides that they need to read the entire object anyway, one can call the `materialize` method to get the decoded `TestHeader`, like so:
```ts
const testHeader = view.materialize();
```

I've also added some benchmarks for the views and they are slightly faster even for the simple case we have in benchmarks now (a `bigint` + some `Bytes<32>`) even when we read all of the fields but the last one. I expect that in a more complex cases (nested classes) the gains might be even bigger.

I've also made two slightly off-topic changes, but hope to include them together in this PR to avoid extra work:
1. Rename `jam-codec` package to just `codec`. The fact it's JAM is kind of obvious and I'd rather avoid that since the name might easily change in the future.
2. Change some of the `Logger` methods to become static on the `Logger` instance. I think the initial design of making them standalone functions was not a great one. `newLogger` still stays to avoid cluttering this PR with unrelated changes, but I'll do that as a separate PR.

Follow up tasks:
- [ ] Create an issue about `Skipper` vs `Decoder` to further improve performance of `View`s.
- [ ] Remove `newLogger` usage.
