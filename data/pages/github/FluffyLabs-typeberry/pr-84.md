Unused is inaccessible memory (it cannot be allocated). If my calculations are correct max segments sizes are:
1. 16MB - readonly
2. 1GB - heap
3. 16MB - stack
4. 16MB - additional readonly

# The solution: 
- added `BasicMemory` class that keeps data (`UIntArray`) and allow to read/write to this array
- added 4 segment classes that wrap `BasicMemory` and care of address offsets 
- added `Memory` class that decides to/from which segment write/read based on address 
- expose setupMemory method that allows to set initial data in memory 

# Known problems:
- sbrk is implemented but is not used yet, also I have no idea how to handle OoM
- memory initialisation in our test runner works but needs more love. It works only if a test has only one initial memory chunk (all currently available tests)

## Comment by @tomusdrw

I don't think this is a good approach, but happy to be proven wrong with some benchmarks.

Design-wise I also think this approach is flawed. Let me explain why.

1. The `Uint8Array` is given to this class externally (via `setup` or imho should be via a `constructor`).
2. You cannot assume that the this `Uint8Array` is backed by some arbitrary array.
3. Actually you even should assume that this `Uint8Array` is backed by a `ArrayBuffer`.
4. It can also just be a partial view of some `ArrayBuffer`.
5. This `ArrayBuffer` or `Uint8Array` is potentially re-used between some invocations, so if a reference is kept externally this code will simply COPY the entire buffer and can't even be optimised by VM to re-use the same memory slot, since both references are active.
6. What's more the method arguments allow for a very inefficient resizing for instance by just adding `1`.

My suggestion would be to either:
1. Change the abstractions here to make sure that what is externally managed is actually externally managed and is managed efficiently. So this method can only request the buffer to be resized not directly control what "resize" actually means.
2. Assume we always have enough memory and have abstractions that take care of the rest.

Also we should consider using `ArrayBuffer`'s `maxBytesLength` option. Resizing them is literally the first paragraph in the description because it's so important :)

## Comment by @tomusdrw

You're conflating the definition of PVM memory with the implementation of the underlying memory for PVM interpreter.

The fact that the heap should always be rounded to a full page does not mean that the `ArrayBuffer` or `Uint8Array` needs to be exactly that size.

Copying any large chunks of memory is a no-go also for resuming. If a PVM program needs 512MB and we keep copying data we will probably need something of a factor of 3-5x of that memory to be able to run it. So it's also not okay for resuming. We need to strictly control where the large allocations happen.

I think we might be on the same page with "virtual allocation" and I really think it wouldn't be an overkill and would actually be much simpler and easier to work with.

It's not clear to me if the memory has to be allocated in a continuous chunks, like in EVM, where we pay for growing the memory by accessing some far indices or if the program can just randomly access any address (in which case we should just allocate memory in pages with a size that is yet to be defined (don't conflate with the GP-based page size)).

But if it's contiguous then we can just do this (if it's not contiguous then memory should contain a `Map` of pages that are just like that, i.e. `PagedMemory { Map<PageIndex, Memory(frombelow) + Offset> }`.
```js
class MemIndex {
  constructor(public readonly idx: number) {
     check(idx > 0 && idx < MAX_MEM && isInteger(idx));
  }
}

class ReadOnlyView {
   constructor(
      public readonly start: MemIndex,
      public readonly end: MemIndex,
      public readonly view: Uint8Array,
   ) {
     check(end.idx  - start.idx >= view.length);
   }

   readByte(address: MemIndex) {
     check(address.idx >= this.start.idx);
     check(address.idx < this.end.idx);
     const internalOffset = address.idx - this.start.idx;
     return (internalOffset < this.view.length) ? this.view[internalOffset] : 0;
   }
}

class WriteableView {
  constructor(
     public readonly start: MemIndex,
     public readonly end: MemIndex,
     public readonly view: Uint8Array,
  ) {
     check(end.idx  - start.idx === view.length);
  }

  // if we still use absolute addressing here creating only a sub-view for Uint8Array might be unnecessary (extra internalOffset calculations).
  write(address: MemIndex, value: Uint8Array) {
    check(address.idx >= this.start.idx);
    check(address.idx < this.end.idx);
    check(address.idx + value.length < this.end.idx);
    // if we only expect small chunks being written like that, we can check that explicitly as well.
    // check(value.length < 4); 

    const internalOffset = address.idx - this.start.idx;
    this.view.set(value, internalOffset);
  }
}

class Memory {
  raw: ArrayBuffer = new ArrayBuffer(INITIAL_MEM_SIZE, { maxByteLength: MAX_MEM_SIZE });
  currentSize = INITIAL_MEM_SIZE;

  viewMut(start: MemIndex, end: MemIndex) {
    check(end.idx >= start.idx);
    while (end.idx > raw.length) {
      this.expand();
    }
    return new WriteableView(start, end, new Uint8Array(this.raw, start.idx, end.idx - start.idx));
  }

  view(start: MemIndex, end: MemIndex) {
    check(end.idx >= start.idx);
    return new ReadOnlyView(start, end, new Uint8Array(this.raw, start.idx, end.idx - start.idx));
  }

  private expand() {
    if (this.raw.length === MAX_MEM_SIZE) {
      throw new OutOfMemoryError();
    }
    this.raw.resize(Math.min(MAX_MEM_SIZE, this.raw.length * 2));
  }
}
```
