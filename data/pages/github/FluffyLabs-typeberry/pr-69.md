# PVM - add support for ecalli instruction

## Pull Request by @mateuszsikora

# What?
This PR introduces support for `ecalli` instruction. It is basically the same pattern what in case of other instructions - ops class, dispatcher class and everything is connected together in pvm class. `ecalli` instruction is very simple - it only sets exit status and host-call identifier in `instructionResult` object so everything should be pretty straightforward to understand 


## Comment by @tomusdrw

```suggestion
  /**
    * A numeric exit parameter of the PVM.
    * 
    * In case of a `status === Result.FAULT` this will be the memory address
    * that triggered the fault.
    * In case of a `status === Result.HOST` this will be the host call index
    * that should be invoked.
    *
    * In any other circumstance the value should be `null`.
    */
  public exitParam: number | null = null;
```


## Comment by @tomusdrw

`exitParam` should be nullified at the beginning of `nextStep`. I think it is incorrect to let it maintain the old value from the previous step.


## Comment by @mateuszsikora

but when it is set then it won't be any next step. it is needed only in 2 cases:
- page fault

## Comment by @mateuszsikora

## Comment by @tomusdrw

From performance PoV we need resume. Host calls will be super frequent, we can't serialize and deserialize the memory every time this happens.

Honestly we will probably even need to re-use the instance between runs (i.e. do not deallocate memory, but rather zeroize it).

Most host calls will resolve locally (like reading from the state), however there might be some that will only resolve on a next run or sth (in that case we might need to snapshot the state or we will keep the instance running).
