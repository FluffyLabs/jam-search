# PVM: branch ops

## Pull Request by @mateuszsikora

# What?

The aim of this PR is to add support for branch instructions. Changes:
1. `RegisterIndexDecoder` is extended to be more generic `NibblesDecoder`.
2. `BranchOps` class is added but it is not fully functional yet.
3. Dispatcher classes are added (`OneOffsetDispatcher`, `OneRegisterOneImmediateOneOffsetDispatcher` and `TwoRegsOneOffsetDispatcher`).
4. Added context object to keep program counter, registers, code, and mask
5. Added implementation of `BranchOps.branch` 
6. Added `LoadOps` and `OneRegisterOneImmediateDispatcher` to handle `LOAD_IMM` instruction
7. Fixed `getNoOfBytesToNextInstruction`
8. Fixed gas calculation

# Why?

1. Not only register indexes are encoded on nibbles. In case of instruction with 2 numbers (2 immediates or 1 immediate and 1 offset) the length of the first number is encoded on nibble.
2. To reduce all branch variants (args and conditions) to one common function and handle it correctly.
3. To handle various kinds of branch arguments and pass it to a proper method of `BranchOps`,
4. I need to have access to program counter in "Ops" classes and somehow get a new program counter from "BranchOps" object
5. Now it was possible - when 1-4 are finished 
6. `LOAD_IMM` is used in tests related to branch instructions 🤦 
7. There was a corner case where the program length was a multiple of 8 and `getNoOfBytesToNextInstruction` returned incorrect result for indexes after the last instruction
8. It was completely incorrect - at the beginning I thought that each instruction costs 2 (from basic tests. In GP each instruction costs 0) but more complicated tests showed that each instruction costs 1 and at the end of each program there is an additional `trap` that costs 1 as well   

# How?

1. `getFirstIndex` is replaced with `getHighNibble`, `getHighNibbleAsRegisterIndex` and `getHighNibbleAsLength`. Similarly in the case of `getSecondIndex`. The new functions are similar but they clamp the result differently.
2. `BranchOps` is similar to other "Ops" classes, the only one difference is that all public methods calls directly or indirectly `branch` function that will handle all cases. 
3. Nothing interesting here - they are exactly the same what other "Dispatchers".
4. PC, registers, mask and code are wrapped into `Context` object and passed down to "Ops" classes.
5. It overrides `nextPc` in context object when the condition is met.
6. Nothing interesting here - they same pattern what we have in case of other instructions.
7. it couldn't find the last "1" in mask (because it doesn't exist) so I added a condition to break the loop when all bits were visited (and a test that checks it).
8. Changed cost of each instruction to 1 and added additional trap at the end.
