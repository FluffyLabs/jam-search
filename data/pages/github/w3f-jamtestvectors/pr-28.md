> Also i am wondering why p_kappa is treated as pre/post state... since there is no way it changes due to `EA` shouldnt it be places in `input`?

This issue has come up frequently in the chat. Given a certain state value `X`:

1. One option is that the "input" should include **only** elements from the block (i.e., header and extrinsic) and "derived values" (i.e. volatile stuff not found in the state nor in the block, but derived from a combination of the two), while anything else is placed in the state—potentially specifying whether it refers to X, X', X†, or X‡.
2. Another option is that the "input" can also contain state components from intermediate or posterior state (i.e., X', X†, X‡).

I initially followed approach 2, but after some discussion, I’ve decided to adhere to approach 1.
2 poses the additional problem that some state bits to be altered in the STF are already in their "dagger" state (e.g. $\rho^†$ in avail assurances STF). Thus doesn't make much sense to heve them both in input and state.

In the end, IMO, either options may work, as long as we’re consistent and explicit about which state bits refer to posterior  or intermediate states. (e.g. see https://github.com/davxy/jam-test-vectors/blob/8a6c01cb12de9ae89cde10f003cb0308444c5f1c/assurances/assurances.asn#L12-L14)

---

I’ll tried to improve the vectors by:
- Consistently specifying the semantics of state items in the ASN.1 syntax files—indicating whether they are posterior or dagger, and whether they are modified by the STF. Currently, there are instances where this level of detail is missing.
- Updating the repository’s root README to reflect the targeted GP version. Although it currently states 0.5.1, the repository already incorporates changes planned for the upcoming 0.5.3 release.
