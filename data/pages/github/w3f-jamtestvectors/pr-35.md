## Comment by @deadline314

> Could you please elaborate a bit on the meaning of the input parameters? The graypaper refers to "pieces" as the 684 byte chunks of the input data that can be processed in parallel. A single piece would then be encoded into 1023 shards 2 bytes each.

Basically, since erasure coding does not allow the data length to be smaller than the size of a data shard, it must be padded to a length of `2 * numPieces`. For tiny spec, this means padding up to `2 * 2 * numPieces` in total.

Here, each piece represents a GF (Galois Field) point, and each GF point consists of 16 bits, which means it is grouped as 2 bytes. This is why the multiplication by 2 is necessary.

However, it would be more appropriate to fix the data length based on the file name. Let me regenerate them accordingly, as this will make things clearer.

## Comment by @deadline314

@arkpar , thanks for your response! Based on the [Gray Paper](https://graypaper.fluffylabs.dev/#/4bb8fd2/1baa001b5701), Erasure Coding is mainly applied in two scenarios. I have categorized the current test vectors accordingly.

### 1. Work Package Bundle Erasure Coding
This encoding method follows the formula:

```math
C_{\lceil |b| / W_E \rceil}\left( \mathcal{P}_{W_E} (\mathbf{b}) \right)
```

- The size of `b` dynamically determines the number of GF points per shard.
- Regardless of the length of `b`, the encoding result always produces a single set of EC shards.

### 2. Segment and Page Proof Erasure Coding
This encoding method follows a fixed formula:

```math
C_6( \mathbf{s}︿P(\mathbf{s}) )
```

- Each shard contains **6 GF points**, equivalent to **12 bytes (24 hex characters)**, since:
  
  ```math
  1 \text{ GF Point} = 2 \text{ bytes} = 4 \text{ hex characters}
  ```

- `C_6` requires **342 data shards**, calculated as follows:

  ```math
  342 \times 12 = 4104 = G
  ```

- Data can be fully allocated into the data shards without any remainder.

I hope this test vector helps reduce misunderstandings and provides a clearer understanding of its application.

## Comment by @deadline314

The encoding and decoding functions for work package bundles and segments are identical.

The only difference lies in the input parameter that determines how many GF Points each shard contains.

Using different bases (${\\lceil |b| / W_E \\rceil}$ or 6) ensures that erasure coding can fully utilize the input data without overflow.

For example, when using {\\lceil |b| / W_E \\rceil}, if the original b is 1000 bytes, the base value will be 2. This means the number of data-carrying points will be:

$$
{\\text{data shard} * \\text{Number of GF points} = 684 * 2 = 1368}
$$

Thus, in the work package bundle scenario, only zero-padding occurs without overflow.

Similarly, for segments and page proofs, since the gray paper defines the segment size as $W_G = 4104$ and specifies that page proofs are padded to ${l = W_G = 4104}$, the original data can be completely converted into GF points when $C_6$ is used.
