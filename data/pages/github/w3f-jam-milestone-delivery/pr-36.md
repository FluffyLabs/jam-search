## Comment by @koute

It might not necessarily make sense to use the time of submission as the only criteria here.

For the sake of argument let's say that [the slowest](https://paritytech.github.io/jam-conformance-dashboard/) implementation is submitted first. The current slowest submission is ~32 times slower than the fastest. Let's say that it takes a week to validate the fastest submission. This would mean that the slowest submission could block the queue for *7 months*.

I think we could give *some* leeway for implementations which fundamentally can't be very fast (e.g. you can't expect a Python implementation to be as fast as a Rust implementation), but we should gently nudge people to be *reasonably* fast within the language they're working in. (And what constitutes "reasonably fast" could probably be inferred by looking at some publicly available benchmarks where people drag race languages against each other.) While the M1 milestone is not supposed to evaluate performance we *do* want performant implementations and should reward those who put the extra effort to make theirs fast! And this is *especially* true for those aiming for the non-light node paths.


## Comment by @koute

Might also be worthwhile to mention something like ", and for the earlier milestones at the discretion of the Foundation". (For example, it wouldn't make sense to accept an M3 milestone submission right now even if an implementation would claim conformance, simply because JAM isn't yet feature complete so it's neither possible nor does it make sense to evaluate M3 at this point in time.)


## Comment by @PieWol

Hey @koute , thanks for the quick review. We have defined the criteria for milestone 1 fuzzing  to successfully complete 1 million steps. Following the calculations from the dashboard you linked, Polkajam is capable of completing these steps in just one hour. So even a ~32 times slower implementation would still be done within two days. Furthermore, we have agreed, together with Davide, to split the 1 million steps in up to 10 parallel runs to mitigate this issue even further. So I hope your concerns about fuzzing delays are void at least for milestone 1. 

Using the submission timestamp for ordering the queue together with our internal evaluation guidelines allows us to process the submissions sequentially without a lot of overhead.
