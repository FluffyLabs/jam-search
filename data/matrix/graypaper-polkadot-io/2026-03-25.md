**jan** (2026-03-25T11:47:00.000Z) [msgid:$IGFfT9qfk8-Ajc2meQ7KcmGKf5xxv9HOiz62NFKwS5w]:
The original rationale was to allow random access into the program, i.e. given an arbitrary program counter how do you tell whether it's valid to jump there? Without the bitmask you're always forced to do a full O(n) scan of the whole program. (Or use a constant-length instruction set encoding, which bloats up the size even more.)

The new gas cost model doesn't require you to scan the full program; fundamentally it only requires you to process the program until the end of the basic block into which you're jumping into.
That said, we have indeed effectively added a full scan requirement in GP 0.8 to simplify things for JAM 1.0, since (in the short-term) we'll be assuming an ahead-of-time recompiler anyway, and prevalidating a program simplifies certain corner cases (which now don't have to be specced because they now can't happen).

Currently the bitmask is also used for the dispatch table at the start of JAM program blobs, where is authorized/refine/accumulate entry points are aligned so that they start at offsets 0/5/10.

You're right that assuming the "every time you instantiate a program you do an O(n) scan" requirement is in place the bitmask is unnecessary. It is however still useful in cases where, for example, you'd want to prevalidate a program at upload time and then be able to jump into it later _without_ validating it again (that's how smart contracts on Polkadot with pallet-revive work), or if we assume that we'll want to relax the requirements and remove the mandatory prevalidation in the future (allowing other execution strategies than O(n) ahead of time recompilation, e.g. recompiler/interpreter hybrids, piece-wice JIT recompilation, etc.).

**jan** (2026-03-25T11:57:00.000Z) [msgid:$WcQ6DkzSoVY_ICktstugrDp9vTNqOIRBwjY5CRbsu4M]:
Also, note, some instructions _do_ use the value of skip to decode the length of their arguments! So you'd still have to encode that length _somehow_ if you'd remove the bitmask.

**jan** (2026-03-25T13:38:00.000Z) [msgid:$PrNWylmhxxzsw06ES5u_jMqb8m1I9FAWRaErOKt-InU]:
Also, note, currently in JAM prevalidation isn't really a thing on the protocol level because for inner VMs you just stuff the raw bytes representing the program into the hostcall and you get a VM instance back (there isn't a separate "upload" nor "compile" step), so there isn't really a way for the client to cache anything (it'd have to hash the program blob before instantiating it, and, at least when I measured with the old gas cost model, with an optimized recompiler like mine always recompiling the program from scratch was faster than hashing it).

Anyway, if you'd like then feel free to try to remove the bitmask (replacing it appropriately), measure the size difference on something substantial (e.g. DOOM; you can find a raw ELF for that in the PolkaVM repo), present how much that would save, and we can consider it. (:
