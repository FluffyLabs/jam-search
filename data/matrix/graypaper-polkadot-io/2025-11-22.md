**sourabhniyogi** (2025-11-22T01:00:00.000Z) [msgid:$tPvARX2Z1oLJl1hPMd7MOAiRCrbzQmCN1o4-7B5fepg]:
Thank you all for chiming in.  I made a mistake in thinking that JAM State would store N00K JAM DA pointers directly and have N00K updates across many cores, but with W\_R=48K (motivated by keeping JAM blocks bounded to under 16-20MB), it cannot.

The solution is to have shard commitments stored in JAM State instead of JAM DA pointers, with each shard holding many JAM DA pointers in JAM DA rather than JAM State.   The refine then only needs to update a small number of shards, where the typical refine will update at most 480 shards (100 byte/shard).  This keeps the work report small, the size of BMT proofs manageable or just replaced with digest updates if the cost for JAM storage is small -- if each key in JAM State needs 100 bytes, then 1MM shards need 100MB (hopefully needing at most 20K DOT...).

The service user, given the need to find something for some key following JAM State into DA, can find its content in JAM DA by finding a DA pointer in JAM State using that K, then reading a shard from JAM DA (which holds another JAM DA pointer), then finally finding the content using that pointer.  Each of these pointers are (wph/segmentroot, indexstart, indexend), guaranteed and audited soon enough.  So its just the usual: solving problems with another layer of indirection.  If you take 1B keys and shard them into 1MM-4MM shards (the first 20-22 bits of the key), each shard has about 250-1K DA pointers.  With some cleverness, you can make the whole thing adaptive so as you need to store more DA pointers across some number of shards, you increase the depth from a small number of bits (say 8) and increase 1 by 1 so the 4K segments in DA always have like 50 refs typically (instead of "20 ought to be good enough for the world").  No Verkle/FRI+STARK/... anything, not even NOMT.

Instead, the service builder who uses N cores has to maintain service updates grouped by shard to ensure that WPs submitted to each core do not conflict on the shards they read and write so that accumulate has no conflicts to resolve.     If it did, the builder would just resubmit a new WP with non-conflicting txs on the next WP batch.

I also made the mistake of thinking accumulate would order txs through some ordered accumulation that resolve multi-core dependencies, but actually, its the _service builder_ who will do that -- by organizing the txs grouped by shard.   Instead of each accumulate assembling a single "rollup block" stitched together across N cores, there are just lots of shard commitments that form N "rollup blocks" from N parallelized accumulates, each of which have txs updating as many as 480 shards.    accumulate just grouping together shard commitments at some stateroot, making sure there is at most ONE commitment for every shard.  Each refine will use state witnesses on previously recorded shard commitment to provide new writes but they will NOT be updating tens of thousands of JAM State keys, but at most like 480.

To take the most common use case of transfers, if Alice sends 1USD to Bob, and it touches the Alice shard, the Bob shard and a shard representing Alices tx + receipt -- well, that single action results in 3 shard commitments.  Another tx from Charlie to Dave will touch 3 different shards, in all likelihood.  If Alice to Bob and Charlie to Dave touch disjoint sets of shards, then the builder can put them in the same WP on the same core.  With W\_R=48K, a refine/core can only output 480 shard commitments, thus each refine/core can output only 160 transfer txns, but across 341 cores you could get 57,440 transactions -- if you were lucky and didn't hit the "birthday paradox" -- if this happens every 6s, that's close to 10K TPS, 10% of a Spammening.    You can definitely do a lot more as multiple cores get hits on the same shard, and so long as the builder queues up WPs with the prereqs, everything should work without too much jamming up at all.

A change of basis is not required.  Thank you all again.
