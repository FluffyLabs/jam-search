1. Happily, the "event ID" parts all made sense and fell into place quite nicely.  For Event ID u64, the JIP-3 approach to Telemetry events is always intra-node -- that is, everyone's Event IDs are generated locally and are never shared except with the telemetry server ... but never \*inter-\*node, so far as I can tell.  This intra-node-only approach is perfect for logging/visualizing the behavior of individual nodes, but it doesn't assist in visualizing the behavior across nodes (unless TART does a lot of amazing guesswork to stitch all the different nodes' eventIDs together!).   The EventID could have optional or required bytes beyond the present u64, to model the key already present in JAM-NP

- epoch (CE131/132): for ticketing (events 80-84)
- work package hash (CE133/134/135): for refining/auditing by builder/guarantor/auditor (90-113)
- erasureRoot (CE137/138/139/140/147): for assuring/DA (events 120-153)
- segmentsRoot (CE148): for assuring/DA (events 160-178)
- preimagehash (CE142/143): for preimages (events 190-199)
- peerID (UP0/..): for peering (events 20-28, 60-61)
- header hash (UP0/CE128/141): for authoring/importing/assuring (events 40-48, 62-68, 11+12?)
Having an additional key (already present in JAM-NP) to support inter-node event analysis could eliminate TART guesswork and map onto other distributed telemetry systems.  What do you think?
