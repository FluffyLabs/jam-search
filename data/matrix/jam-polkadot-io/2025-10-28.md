**igankevich** (2025-10-28T09:26:00.000Z) [msgid:$u00I_ZSaHN1myZIPz43KIIFaq0aHrIqpJTow50CZBrY]:
It would be awesome to port applications of course 😃

Arguably the most valuable offer of application container platforms is their hubs. Hence, I think, the most straightforward approach to port an application would be to pull Docker/LXC/whatever image from a hub, convert it to CoreVM FS image and run the entry point inside CoreVM. This is how Singularity entered the scene as a new application container platform back in the days: you just type singularity shell docker://ubuntu:latest and it "steals" Ubuntu image from the Docker hub, converts it to its own format, and launches the shell. It should be possible (and not that difficult!) to write a similar CLI tool for CoreVM.

Please also keep in mind that there is no Internet access inside CoreVM, so most Docker commands (e.g. docker pull, lxc create) inside CoreVM will not work. This kinda defeats the purpose of porting application container platforms to CoreVM, isn't it? (It might not work outside either because CoreVM needs riscv64 architecture and most images are built for different architectures.)

My point is that running LXC/Docker inside CoreVM is not that transparent due to a lack of access to hubs. A more user-friendly way of running "old" containerized applications on CoreVM would be to do that directly via a converter tool that I mentioned above. Eventually it would make sense to create an on-chain hub with riscv64 images stored in e.g. IPFS or something to not depend on web2 hubs.

**alice_und_bob** (2025-10-28T11:27:00.000Z) [msgid:$cpnqkbhNNdsTEToQpCZvklOOoV3Sb3Gbc_Vm3axc03g]:
what I typically find very helpful when considering ideas like these in systems design is to think in terms of tradeoffs. What am I gaining and what am I giving? On the most basic level in system properties

Typical Web2 properties are: large amounts of storage, compute, low latency...
Typical Web3 properties are: censorship resistance, verifiability + privacy if you add ZK

So when considering an idea like "nginx on JAM", you can ask: what do I get and what do I give?

You might get a time saver on not having to reimplement the stack and you gain verifiability, but what is that good for for a simple web server? And what you give is performance and more money.

So the tradeoffs don't yield a very attractive result in this case
