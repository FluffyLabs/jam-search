**davxy** (2026-02-18T08:27:00.000Z) [msgid:$ygVLexvAHXvtyVJ6t3mYc2opLptk47tbo5VwIosfWtU]:
There was an inconsistency in the engine (to not call it a bug XD).
Ticket ID was not encoded as a compact integer; instead, we used a fixed-length encoding (here 1 byte).
Under normal conditions this had no impact, since the ticket ID was expected to be 0 or 1.
However, the fuzzer can mutate this field to any value in the range \[0..255\]. For values >= 128, the issue manifests: we encode them in a single byte, whereas we should be using the general integer codec (which uses 2 bytes here).

**davxy** (2026-02-18T08:35:00.000Z) [msgid:$uskaBP-eESFf_MDHD_ZvhVPDnz4nhiwN9PtmU-P22A8]:
Even if this is a delicate moment for releasing breaking changes in the fuzzer, IMO for what concerns **this** particular issue we can release the fix **NOW** and include it in the 0.7.2 fuzzer.
Including it in 0.7.2 should not introduce material risk, since targets will reject the block in both scenarios:

- Before: rejection due to an invalid ticket signature.
- After: rejection due to invalid ticket encoding.

The difference is limited to the stage at which the block is rejected.
The validation logic does not assert the specific reason for failure. This is intentional, as block processing may follow different internal paths and there is no mandated failure ordering.
In short, if a block import is expected to fail, the precise rejection condition is not relevant to the test outcome.
